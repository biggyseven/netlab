FICHE / 001 · ADRESSAGE OUTIL DISPONIBLE

Adressage IPv4 et calcul CIDR

Déterminer le réseau auquel appartient une adresse, déduire le masque et identifier la plage utilisable sans calculer chaque bit à la main.

EnvironnementCalculateur NETLAB · Windows / Linux
PrérequisAdresse IPv4 et préfixe CIDR
ÉtatCalculateur testé · captures à ajouter

01 Objectif et principe

Un préfixe CIDR indique le nombre de bits réservés à la partie réseau. Pour 192.168.10.25/24, les 24 premiers bits représentent le réseau et les 8 bits restants la partie hôte.

Le calcul produit l'adresse réseau, le masque, le broadcast, le wildcard et la plage d'adresses utilisables. Les cas /31 et /32 suivent un traitement particulier.

02 Procédure et valeurs de référence

  1. Ouvrir le calculateur IPv4 de NETLAB.
  2. Saisir une adresse avec son préfixe, par exemple 192.168.10.25/24.
  3. Cliquer sur Calculer, puis lire le réseau, le masque, le broadcast et la plage d'hôtes.
  4. Comparer les valeurs à ce tableau, puis recommencer avec /30, /31 et /32.
EntréeRéseauBroadcastHôtes utilisables
192.168.10.25/24192.168.10.0192.168.10.255192.168.10.1 à .254 (254)
10.0.5.5/3010.0.5.410.0.5.710.0.5.5 à .6 (2)
10.0.5.5/3110.0.5.410.0.5.5Les deux adresses (2)
10.0.5.5/3210.0.5.510.0.5.510.0.5.5 (1)

Valeurs de référence pour contrôler le calculateur, pas des mesures prises sur un réseau actif.

03 Commandes de vérification

Après avoir configuré une interface avec une adresse issue de l'exercice, comparer l'adresse et la route réellement appliquées au système.

WINDOWS · CMD / POWERSHELL
ipconfig /all
route print
ping -n 4 192.168.10.1
LINUX · TERMINAL
ip -br address
ip route
ping -c 4 192.168.10.1

Remplacer 192.168.10.1 par la passerelle réelle. Un ping peut être bloqué par un pare-feu et ne prouve pas, à lui seul, une panne IP.

04 Contrôle et preuves à conserver

  • Comparer les sorties /24, /30, /31 et /32 au tableau de référence.
  • Vérifier qu'une adresse mal formée et un préfixe supérieur à /32 déclenchent une erreur.
  • Capturer le calcul /24 complet et un cas particulier /31.
  • Ajouter une capture de ipconfig /all ou ip -br address après une configuration réelle.
État des essais : les cas limites du moteur de calcul ont été contrôlés. Les captures d'une configuration réseau réelle restent à ajouter.
FICHE / 002 · INFRASTRUCTURE À RÉALISER DANS GNS3

Construire un réseau PME segmenté

Mettre en place une passerelle sécurisée, transporter plusieurs VLAN sur un trunk 802.1Q et contrôler les communications entre zones.

EnvironnementGNS3 · pfSense · switch manageable
SegmentsAdministration · Utilisateurs · Serveurs
ÉtatPack LAB 001 prêt à adapter · tests à exécuter

01 Plan d'adressage proposé

ZoneVLANSous-réseauPasserelle prévue
Administration10192.168.10.0/24192.168.10.1
Utilisateurs20192.168.20.0/24192.168.20.1
Serveurs30192.168.30.0/24192.168.30.1

Plan de départ. Les passerelles seront portées par les interfaces VLAN de pfSense dans une architecture router-on-a-stick.

Point d'architecture important

Le switch L2 transporte les VLAN, mais n'effectue pas le routage entre eux. Le port relié à pfSense doit être un trunk 802.1Q. Les VLAN sont créés et assignés dans pfSense, qui porte les passerelles et applique les règles inter-VLAN.

02 Construire et câbler dans GNS3

  1. Ajouter un nœud NAT ou Cloud pour représenter l'accès WAN du laboratoire.
  2. Relier le WAN de pfSense au nœud externe, puis son interface LAN au switch manageable.
  3. Ajouter trois postes de test et un serveur Ubuntu, puis les raccorder aux ports d'accès prévus.
  4. Vérifier que chaque lien est connecté et que les interfaces utilisées existent sur les appliances choisies.

03 Créer les VLAN et le trunk

  1. Sur le switch, créer les VLAN 10, 20 et 30.
  2. Configurer le port vers pfSense en trunk et autoriser les VLAN 10, 20 et 30 avec le marquage 802.1Q.
  3. Configurer les ports des postes en access, chacun dans son VLAN.
  4. Dans pfSense, ouvrir Interfaces → Assignments → VLANs, créer les trois VLAN sur l'interface physique parent puis les assigner.
  5. Attribuer les passerelles prévues (.1/24). Activer le DHCP seulement sur les segments qui doivent distribuer des adresses automatiquement.
EXEMPLE · CISCO IOS UNIQUEMENT
vlan 10
 name ADMIN
vlan 20
 name USERS
vlan 30
 name SERVERS
!
interface GigabitEthernet0/1
 description TRUNK_VERS_PFSENSE
 switchport mode trunk
 switchport trunk allowed vlan 10,20,30
!
interface GigabitEthernet0/2
 description POSTE_ADMIN
 switchport mode access
 switchport access vlan 10
 spanning-tree portfast
!
interface GigabitEthernet0/3
 description POSTE_USERS
 switchport mode access
 switchport access vlan 20
 spanning-tree portfast
!
interface GigabitEthernet0/4
 description SERVEUR
 switchport mode access
 switchport access vlan 30
 spanning-tree portfast

Exemple à adapter au modèle et aux ports disponibles. Les appliances Ethernet switch de GNS3 n'acceptent pas nécessairement la syntaxe Cisco IOS.

04 Définir les règles de sécurité

  • Administration : autoriser uniquement les flux nécessaires à l'administration des équipements.
  • Utilisateurs : autoriser la sortie Internet requise, sans accès libre au VLAN Administration.
  • Serveurs : autoriser seulement les services nécessaires depuis les segments autorisés.
  • Appliquer le moindre privilège et vérifier l'ordre des règles sur chaque interface pfSense.

Les règles pfSense sont évaluées sur l'interface où le trafic entre. Une règle sur le VLAN Utilisateurs ne remplace pas les contrôles sur les autres interfaces.

FICHE / 003 · SUPERVISION EN PRÉPARATION

Superviser les hôtes avec Zabbix

Déployer une supervision centralisée pour suivre la disponibilité, les ressources et les services d'un petit réseau d'entreprise.

EnvironnementUbuntu Server · Zabbix · Agent 2
Cibles prévuesLinux · Windows · équipements SNMP
ÉtatProcédure préparatoire · installation à valider

01 Architecture et flux

Le serveur Zabbix et son interface Web sont hébergés sur Ubuntu Server. Les agents sont installés sur les machines suivies. Dans le plan NETLAB, le serveur de supervision est placé dans le VLAN 30, avec des règles limitées aux hôtes supervisés.

FluxPort par défautUtilisation
Serveur → agentTCP 10050Contrôles passifs
Agent → serveurTCP 10051Contrôles actifs
Navigateur → interface WebTCP 80 / 443Consultation du frontend
Équipement → collecteur SNMP trapUDP 162Traps SNMP, si déployés

Ouvrir uniquement les flux réellement utilisés et limiter les sources aux adresses des composants concernés. Les ports peuvent être modifiés.

02 Préparer le serveur

  1. Créer une VM Ubuntu Server avec une adresse stable dans le VLAN Serveurs.
  2. Définir le nom d'hôte, la passerelle et le DNS, puis vérifier la connectivité IP.
  3. Choisir une version Zabbix compatible avec la version d'Ubuntu et la base de données retenue.
  4. Utiliser le guide officiel pour sélectionner le dépôt et les paquets adaptés, puis installer serveur, frontend, base de données et agent.
  5. Consigner la version choisie et les paramètres réellement installés.
Important : les commandes d'installation dépendent de la version et de la distribution. Cette fiche renvoie au guide officiel plutôt que de figer une commande susceptible de devenir obsolète.

03 Déclarer les agents

  1. Installer Zabbix Agent 2 sur les machines Linux et Windows ciblées, avec une version compatible avec le serveur.
  2. Configurer le serveur autorisé, la destination active et le nom d'hôte.
  3. Dans l'interface Web, créer l'hôte, renseigner son interface et choisir un modèle adapté au système.
  4. Attendre la collecte, puis contrôler la disponibilité de l'agent et les dernières données reçues.
EXTRAIT · ZABBIX_AGENT2.CONF
Server=<IP_SERVEUR_ZABBIX>
ServerActive=<IP_SERVEUR_ZABBIX>:10051
Hostname=<NOM_HOTE_IDENTIQUE_DANS_ZABBIX>

Remplacer les valeurs entre chevrons. Pour les contrôles passifs, limiter Server à l'adresse du serveur ou du proxy autorisé. Hostname doit correspondre au nom de l'hôte dans l'interface.

04 Contrôler les services et les ports

UBUNTU SERVER · SERVICES
sudo systemctl status zabbix-server
sudo systemctl status zabbix-agent2
sudo journalctl -u zabbix-server -n 50 --no-pager
sudo journalctl -u zabbix-agent2 -n 50 --no-pager
sudo ss -lntup | grep -E '10050|10051'
WINDOWS · POWERSHELL
Get-Service -Name "*Zabbix*"
Test-NetConnection -ComputerName <IP_AGENT> -Port 10050
Test-NetConnection -ComputerName <IP_SERVEUR_ZABBIX> -Port 10051

Le test TCP 10050 se lance du serveur vers l'agent pour un contrôle passif. Le test TCP 10051 se lance de l'agent vers le serveur pour un contrôle actif. N'exécuter que le test correspondant au mode configuré.

05 Valider la collecte et les alertes

  • L'hôte apparaît disponible dans l'interface Zabbix.
  • Les dernières données affichent des valeurs récentes pour CPU, mémoire et disponibilité.
  • Un déclencheur de test passe à l'état attendu lors d'un événement contrôlé.
  • Une notification est reçue par le canal configuré après un test volontaire.
  • Les règles pfSense n'exposent pas les ports Zabbix aux réseaux non autorisés.

06 Captures à intégrer au portfolio

  • Tableau de bord avec hôtes déclarés.
  • Écran Latest data avec valeurs récentes.
  • État d'un agent Linux et d'un agent Windows.
  • Événement de déclencheur et preuve de réception d'une notification.
État des résultats : installation, agents, collecte et notifications restent à réaliser et à capturer. Aucun hôte n'est annoncé comme supervisé avant les essais.
